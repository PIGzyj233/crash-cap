# Import Complete Symbol Pairs Independently of Builds

Quality assurance users may possess only compiled binaries and PDBs supplied by different teams at different times. The decisions below were confirmed on 2026-09-03. The [implementation design](../qa-symbol-import-implementation-design.md) records the accepted Q19–Q21 resolutions; current delivery and acceptance scope are maintained in the [first-launch guide](../qa-symbol-import-guide.md).

A Symbol Import is independent of Build Publications. The subsequent direction in [ADR-0018](0018-search-uploaded-symbol-pairs-platform-wide.md) removes mandatory Workspace selection for this import: verified pairs become platform-wide symbol candidates while their provenance is retained. DMPs and formal Build Publications retain their Workspace association. Every submitted module must include both its binary and its matching debug file in the same import; different complete module pairs may arrive in different imports. Collecting one half now and accepting its counterpart through a later independent import is outside this workflow. This is a submission requirement, not a requirement for two network transfers to finish at the same instant. Individually received or verified bytes do not by themselves establish a Verified Symbol Pair.

The complete module pair is the unit of acceptance and failure isolation. When one pair in a multi-module import is invalid, other complete, verified pairs may become available; the browser reports the outcome for each pair. An invalid pair does not make a valid pair unusable.

A useful report with reliable symbols can be accepted for QA investigation even when no formal Build or release version can be resolved. Symbol availability and Build Resolution are presented separately. Unresolved Build evidence does not justify inventing a Build, a commit, or a release association. Existing Build identity, Manifest expectations, sealing, and Build-scoped Artifact meanings remain intact.

The first delivery must let QA users upload DMPs, supply complete symbol pairs, and inspect reports through the browser without Git, source code, a publishing environment, or command-line configuration. It accepts multiple files and directory selection, discovers complete pairs, and reports results per pair. Archive files are extracted locally before selection; direct archive import is outside the first delivery. Source text remains optional.

Newly available symbol pairs trigger automatic reanalysis of affected existing DMPs. Reanalysis creates immutable Analysis Runs, retains historical results and change evidence, and does not create additional Occurrences. New reliable evidence may correct an earlier conclusion; an aggregate quality score alone cannot determine whether a new result should become Current Analysis.

Automatic reanalysis preserves the previous useful Current Analysis when a temporary symbol-service failure degrades the new report. Retain the new diagnostic Run and retry within a bounded budget. Q16 confirms a specific mixed-change exception: a new Run may become Current when it improves reliable crash-business function or line evidence, preserves existing key business evidence, and loses only some system-symbol information because of an identified temporary service failure. Show that system information is temporarily unavailable and continue bounded retry. Temporary loss of key business evidence always retains the previous useful Current Analysis. Each report remains the result of one complete Run; frames from different Runs are never stitched together.

These decisions add an eligibility requirement to ADR-0009 for this automatic workflow. Creation order continues to select among eligible Runs. Q21 in [ADR-0021](0021-promote-current-analysis-by-versioned-evidence.md) accepts evidence-v1, including incomparable candidates and verified corrections. Q19/Q20 establish the supporting contract, catalog, planning, and dispatch decisions. Exact versions and bounded retries are recorded in the [protocol](../qa-symbol-import-protocol.md); old-version continuity is outside the first-launch scope.

Related symbol events for the same Occurrence may be coalesced before analysis. The initial product target is a 30-second coalescing window with at most 60 seconds of coalescing delay. Queueing and analysis execution time are separate; this is not a report-completion deadline. Implementation must validate these bounds and retain the latest applicable symbol evidence when events are combined.

QA may supply Reported Test Labels for filing and filtering investigations without a resolved Build. These annotations are explicitly identified as manually supplied and never drive symbol matching or establish a verified Build or Version association. Repeated uploads of the same DMP in one Workspace retain one Occurrence and preserve each submission's labels, time, and source. Differing annotations are visible rather than silently overwritten or automatically adjudicated as the correct release.

The trade-off is an additional import lifecycle alongside the exact Build publication lifecycle. In return, QA does not need to assemble a complete release Manifest, while the platform retains the stronger provenance and immutability guarantees of real Builds. Requiring complete pairs avoids a user-facing collection of unrelated half-submissions. [ADR-0018](0018-search-uploaded-symbol-pairs-platform-wide.md) records platform-wide symbol availability and Workspace-local module roles, superseding the earlier reference-based design in ADR-0016. [ADR-0017](0017-keep-symbol-identity-conflicts-explicit-until-verified-recovery.md) records identity-conflict isolation and recovery.
